§01

Start here

For whoever — or whatever — picks this up

GDPRcompliant.eu is a free scanner for European companies that opens a numbered, shareable case, answers every finding with something the customer can act on, and keeps watching afterwards. The sentence that settles most arguments: everyone else hands European companies a list of problems; this hands them a plan and the things that close it.

The design is finished. The engine is not. Phase 0 built and smoke-tested twelve screens driven by a single fixture; phases 1 to 6 stand at 0 of 102, all blocked behind one open task.

# clone, then
cat HANDOFF.md          the entry point, written for an agent
node scripts/tasks.mjs next
X-10  Clickthrough assembly and review with Frits (S, phase 0)

node scripts/tasks.mjs claim X-10 --as builder
node scripts/tasks.mjs done X-10 --note "signed off"
The gate is structural, not a promise

F-01 — the first foundation task — depends on X-10, Frits's sign-off on the prototype. The tool will not offer phase 1 work to anyone until that closes, and editing the dependency to unblock yourself is the one move explicitly out of bounds. Everything downstream inherits the gate through F-01.

The prototype is the design specification, not a sketch. apps/prototype/styles.css is the real design system and ports to the app unchanged at F-01. fixtures/companies/eksempelbutik.json becomes a real test fixture in phase 2, and its shape is the contract. Only the framework glue is disposable — it is vanilla on purpose.

Before changing any screen, read apps/prototype/smoke.mjs. Its 430 assertions are not a formality: each block is a product rule turned into a check. A finding cannot exist without a remedy. The case page shows exactly one current step. A clean site is a pass, never a failed test. Copy may not narrate the interface. Quoted law must match the corpus character for character. Agent prompts must name the real domain and hostnames, never "this site".

§02

How agents claim work

One file per task · no merge conflicts by construction

Each task is its own markdown file with flat frontmatter. Claiming, working and completing touch exactly one file, so two agents working in parallel never collide in git. The CLI is dependency-aware — it only ever offers work whose foundations are actually finished.

# what can be started right now
node scripts/tasks.mjs next
X-01  Prototype scaffold and design system (M, phase 0)

# take it, work, then close it
node scripts/tasks.mjs claim X-01 --as design-agent
node scripts/tasks.mjs done X-01 --note "tokens, themes, locale switch"

# status, any time — reads the files, so it cannot drift
node scripts/tasks.mjs board
node scripts/tasks.mjs check   → ok 107 tasks, no integrity problems

Two refusals are built in, because they're the ways task boards normally rot. done refuses while acceptance criteria are unticked. claim refuses when a dependency is unfinished, and names which one.

§04

The six that actually decide this

Where to look when you want to know if it's going well

X-10

Your sign-off

The gate. Everything downstream waits on it, so a slow review here is the cheapest delay in the whole plan and a rushed one is the most expensive.

S-03

Banner detection and refusal automation

The hardest task in phase 2 and the one the entire wedge rests on. When it can't find a refusal path it must say so rather than pass a site it never actually tested.

A-07

The verifier gate

Pulled forward into phase 2 because the policy reader needs it. Nothing enters the graph without evidence and a citation that mechanically resolves. The load-bearing safety component.

I-02

Jurisdiction bindings

Cheap now, a rewrite later. No article number may appear in detector code. Skip this and the product is permanently Danish.

T-01

The fixture site suite

Twenty-five deliberately broken websites with known-correct expectations. Its coverage is the ceiling on how much anyone can trust the scanner.

R-02

No finding without a remedy

Half a day of work that turns the product's central promise into a database constraint. It's what stops this decaying into the problem-list tool we set out not to build.

§05

Testing, because you won't be doing it

Nine layers · one command · a manual list under fifteen items

This is harder than usual for three reasons: the system reads the live internet, which changes; it uses a language model, which is non-deterministic; and it makes claims about the law, where being confidently wrong is worse than being silent. Each layer exists for a specific one of those.

LayerWhat it catchesTask
Fixture sites25 deliberately broken websites with known-correct expectations — including 4 clean ones that must produce zero findings. A scanner that cries wolf is worse than none.T-01
Deterministic replayCI never touches the live internet. A missing cassette is a hard error, never a silent live call. A flaky suite is a suite nobody trusts.F-09
Citation resolutionEvery citation resolves to a real paragraph and every quote is confirmed by exact substring match — in code, not by asking a model. The cheapest high-value test here.T-03
Schema conformanceNo model output enters unvalidated; a call site without validation fails the build.T-04
Behavioural evalsLabelled scenario sets with declared thresholds, tracked over time, run against the self-hosted model.T-05
AdversarialInjection in page text, comments, alt text, CSS, the policy, the DPA. Plus cloaking, resource exhaustion, and attempts to use the scanner as a proxy.T-06
BoundariesCross-tenant reads, writes, joins, exports and invitation links, tried on every push. Plus the jurisdiction matrix.T-07/08
JourneysScan → fix → re-check → close. Invite → complete → register fills. Export, delete, prove it's gone.T-09
Canary corpus200 real sites nightly. Fixtures prove we built what we designed; the canary proves it still works on the actual internet.T-10

Invariants — enforced at build time, so whole bug categories can't exist

  • A finding cannot be persisted without a remedy, or without evidence
  • A new table without a row-level-security policy fails lint
  • A table without a declared retention rule fails CI
  • An article number appearing in detector code fails lint
  • The words certificate, approved, or compliant-as-a-verdict in customer-facing copy, in any locale, fail the build
  • Identical scans produce byte-identical finding sets

One command decides whether it's fit to hand over — pnpm run gate — running every suite, the canary comparison and the invariants, printing a single verdict with a named owner for anything red. Red is a stop, not a caveat. What stays manual is deliberately tiny: does the case page read well printed, does the Danish sound like Danish, does the trust page look like a seal to someone glancing at it. Things that need eyes and taste, which is exactly why everything else must not.

§06

What is still open

Three, and only the first blocks anything

  1. The sign-off. Click through the prototype and close X-10. Everything else in the plan waits on it, so a slow review here is the cheapest delay available and a rushed one is the most expensive.
  2. How many agents in parallel. Phase 1 supports three or four without collision — foundations, schema and the test harness are largely independent. Phase 2 opens wider.
  3. Whether to deploy the prototype anywhere permanent, so it can be forwarded without a Claude link.

Nothing else needs deciding to start. The stack, the repo layout, the test strategy and the order of work are all settled in PLAN.md and TESTING.md, and where they turn out to be wrong the working agreement says to raise it in the task log rather than quietly build something else.
